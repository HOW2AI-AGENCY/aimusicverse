# Feature Specification: Оптимизация производительности и UX-редизайн мобильного интерфейса

**Feature Branch**: `036-mobile-perf-ux-redesign`
**Created**: 2026-06-28
**Status**: Draft
**Input**: User description: "анализ, оптимизация, улучшение производительности и создание дизайна. акцент на мобильные экраны, простоту и минимализм, продвинутый пользовательский опыт, удобный в обслуживании и настройке"

## User Scenarios & Testing _(mandatory)_

### User Story 1 - Мгновенный отклик на мобильном (Priority: P1)

Пользователь открывает MusicVerse AI в Telegram на мобильном телефоне и получает мгновенный, плавный интерфейс без задержек, рывков и белых экранов. Все переходы между экранами происходят за доли секунды. Скролл треков в библиотеке плавный даже при сотнях элементов. Действия (лайк, воспроизведение, переключение версий A/B) дают немедленную визуальную обратную связь.

**Why this priority**: Производительность — главный фактор удержания в мобильных приложениях. 53% пользователей покидают страницу, если она грузится дольше 3 секунд. Текущий бандл 918KB близок к лимиту 950KB, а 33 файла >500 строк создают риск медленного парсинга на слабых устройствах.

**Independent Test**: Открыть приложение на бюджетном Android-устройстве (Pixel 5 или аналог), выполнить полный цикл: запуск → библиотека → воспроизведение трека → генерация → студия. Каждый переход должен быть <300мс, FPS не должен падать ниже 55.

**Acceptance Scenarios**:

1. **Given** пользователь открывает приложение в Telegram, **When** первый экран загружается, **Then** интерактивный контент отображается менее чем за 2 секунды (TTI)
2. **Given** пользователь листает библиотеку с 200+ треками, **When** скроллит быстро, **Then** рендеринг остаётся плавным (≥55 FPS), без белых пробелов в виртуализированном списке
3. **Given** пользователь переключает экраны (библиотека → генерация → студия), **When** тапает по навигации, **Then** переход происходит за <300мс без мерцаний
4. **Given** пользователь нажимает лайк или переключает версию A/B, **When** действие выполняется, **Then** UI обновляется оптимистично за <100мс до ответа сервера

### User Story 2 - Минималистичный и чистый дизайн (Priority: P1)

Пользователь видит лаконичный, современный интерфейс без визуального шума. Каждый экран содержит только необходимые элементы. Типографика чёткая и читаемая. Цвета используются осмысленно — для акцентов и навигации, не для декорации. Белое пространство (negative space) создаёт ощущение «дыхания». Иконки понятны без подписей. Дизайн следует принципу «одно действие — один экран».

**Why this priority**: Минимализм напрямую влияет на конверсию и время обучения. Упрощённый интерфейс снижает когнитивную нагрузку, что особенно важно для мобильного контекста — маленький экран, отвлечения, одна рука.

**Independent Test**: Показать каждый экран 5 новым пользователям. Каждый должен за 10 секунд определить: (1) что делает экран, (2) какое главное действие, (3) как вернуться назад. Успех: 4 из 5 отвечают правильно.

**Acceptance Scenarios**:

1. **Given** пользователь открывает любой экран, **When** смотрит на интерфейс, **Then** видит не более 1 основного действия (CTA) и не более 3 вторичных
2. **Given** пользователь смотрит на типографику, **When** читает текст на мобильном, **Then** основной текст ≥14px, заголовки контрастны, межстрочный интервал ≥1.4
3. **Given** пользователь видит экран генерации, **When** оценивает визуальный шум, **Then** количество визуально отличимых элементов ≤7 (закон Миллера)
4. **Given** пользователь просматривает библиотеку, **When** видит карточку трека, **Then** карточка содержит только: обложку, название, исполнителя, длительность и кнопку воспроизведения

### User Story 3 - Продвинутые жесты и микровзаимодействия (Priority: P2)

Пользователь управляет приложением с помощью интуитивных жестов: свайп для навигации между треками, долгое нажатие для контекстного меню, двойной тап для лайка, pull-to-refresh для обновления. Каждое взаимодействие сопровождается тактильной обратной связью (haptic), плавными анимациями и звуковыми микро-подсказками. Жесты настраиваются в профиле пользователя.

**Why this priority**: Продвинутые жесты превращают утилитарное приложение в удовольствие от использования. Они увеличивают скорость навигации и создают эмоциональную привязанность.

**Independent Test**: Дать пользователю задачу «найди трек и добавь в плейлист» без объяснения интерфейса. Если пользователь использует хотя бы 2 жеста (свайп, долгое нажатие, двойной тап) — жесты обнаруживаемы.

**Acceptance Scenarios**:

1. **Given** пользователь в плеере, **When** свайпает горизонтально, **Then** переключается на следующий/предыдущий трек с плавной анимацией
2. **Given** пользователь долго нажимает на трек, **When** удерживает 500мс, **Then** появляется контекстное меню с haptic-откликом
3. **Given** пользователь настраивает жесты, **When** открывает настройки, **Then** может включить/выключить каждый жест и настроить чувствительность

---

### User Story 4 - Удобная настройка и персонализация (Priority: P2)

Пользователь может настроить интерфейс под себя: выбрать тему (светлая/тёмная/авто), изменить размер текста, настроить жесты, управлять уведомлениями, выбрать качество воспроизведения. Все настройки группированы логично и доступны в 2 тапа из любого экрана. Изменения применяются мгновенно без перезагрузки.

**Why this priority**: Персонализация увеличивает время в приложении и снижает отток. Настраиваемый интерфейс — признак зрелого продукта.

**Independent Test**: Пользователь открывает настройки, меняет 3 параметра (тема, размер текста, жест). Все изменения видны мгновенно, сохраняются после закрытия приложения.

**Acceptance Scenarios**:

1. **Given** пользователь на любом экране, **When** хочет открыть настройки, **Then** достигает экрана настроек за ≤2 тапа
2. **Given** пользователь переключает тему, **When** выбирает тёмную тему, **Then** интерфейс обновляется за <200мс без перезагрузки
3. **Given** пользователь изменяет размер текста, **When** выбирает «крупный», **Then** все текстовые элементы масштабируются пропорционально
4. **Given** пользователь закрывает и заново открывает приложение, **When** возвращается, **Then** все настройки сохранены

---

### User Story 5 - Обслуживаемый и модульный UI (Priority: P3)

Разработчик может легко модифицировать любой экран приложения. Компоненты переиспользуемы, стилистически единообразны и документированы. Добавление нового экрана занимает <30 минут по шаблону. Дизайн-система описана и поддерживается актуальной. Изменение цветовой палитры или типографики затрагивает всё приложение через одну точку конфигурации.

**Why this priority**: Обслуживаемость — долгосрочная инвестиция. С 987 компонентами и 347 хуками проект уже сложен, и без модульности стоимость изменений будет расти экспоненциально.

**Independent Test**: Разработчик создаёт новый экран с 3 стандартными компонентами (карточка, список, кнопка). Должен уложиться в 30 минут, не создавая ни одного нового UI-примитива.

**Acceptance Scenarios**:

1. **Given** разработчик хочет добавить новый экран, **When** использует существующие компоненты, **Then** создаёт полный экран за <30 минут
2. **Given** дизайнер меняет основной цвет бренда, **When** обновляет одну переменную, **Then** все экраны автоматически обновляются
3. **Given** разработчик ищет компонент, **When** открывает Storybook, **Then** находит документированный пример с API и вариантами

---

### Edge Cases

- Что происходит при экстремально медленном соединении (2G)? Должен отображаться skeleton-UI с прогрессом загрузки, а не белый экран.
- Как ведёт себя интерфейс на очень маленьких экранах (320px ширина)? Все элементы должны оставаться доступными без горизонтальной прокрутки.
- Что если пользователь открывает приложение на планшете/десктопе? Интерфейс должен масштабироваться, сохраняя читаемость и удобство.
- Как обрабатывается потеря сети во время взаимодействия? Оптимистичные обновления откатываются с понятным уведомлением.
- Что если пользователь отключил все анимации в настройках ОС (prefers-reduced-motion)? Все анимации заменяются мгновенными переходами.

## Requirements _(mandatory)_

### Functional Requirements

**Производительность:**
- **FR-001**: Приложение ДОЛЖНО загружать интерактивный контент (TTI) за <2 секунды на устройствах среднего класса
- **FR-002**: Переходы между экранами ДОЛЖНЫ занимать <300мс
- **FR-003**: Скролл списков ДОЛЖЕН поддерживать ≥55 FPS при виртуализации
- **FR-004**: Размер бандла ДОЛЖЕН оставаться ≤950КБ (gzip), с целью снижения до ≤880КБ
- **FR-005**: Lazy loading ДОЛЖЕН применяться ко всем маршрутам и тяжёлым компонентам (>50КБ)

**Дизайн и UX:**
- **FR-006**: Каждый экран ДОЛЖЕН следовать принципу «одно основное действие» — один CTA, ≤3 вторичных
- **FR-007**: Минимальный размер области касания ДОЛЖЕН быть 44×44px
- **FR-008**: Типографика ДОЛЖНА использовать шкалу размеров: 12/14/16/20/24/32px
- **FR-009**: Все цвета ДОЛЖНЫ определяться через CSS-переменные дизайн-токенами
- **FR-010**: Анимации ДОЛЖНЫ уважать `prefers-reduced-motion` и быть отключаемыми в настройках

**Жесты и взаимодействия:**
- **FR-011**: Свайп горизонтальный ДОЛЖЕН переключать треки в плеере
- **FR-012**: Долгое нажатие (500мс) ДОЛЖНО вызывать контекстное меню с haptic-откликом
- **FR-013**: Двойной тап ДОЛЖЕН ставить/убирать лайк с анимацией
- **FR-014**: Pull-to-refresh ДОЛЖЕН обновлять текущий экран
- **FR-015**: Все жесты ДОЛЖНЫ быть настраиваемыми (вкл/выкл, чувствительность)

**Настройки и персонализация:**
- **FR-016**: Пользователь ДОЛЖЕН иметь доступ к настройкам за ≤2 тапа из любого экрана
- **FR-017**: Переключение темы ДОЛЖНО применяться мгновенно (<200мс) без перезагрузки
- **FR-018**: Настройки ДОЛЖНЫ сохраняться между сессиями (localStorage + серверная синхронизация)
- **FR-019**: Пользователь ДОЛЖЕН иметь возможность изменить размер текста (малый/средний/крупный)

**Обслуживаемость:**
- **FR-020**: Все UI-компоненты ДОЛЖНЫ быть документированы в Storybook с примерами и вариантами
- **FR-021**: Цветовая палитра ДОЛЖНА управляться через единый конфигурационный файл дизайн-токенов
- **FR-022**: Компоненты ДОЛЖНЫ быть ≤300 строк кода (вместо текущих 500+)
- **FR-023**: Шаблон нового экрана ДОЛЖЕН позволять создать функциональную страницу за <30 минут

### Key Entities

- **DesignToken**: цвета, типографика, отступы, тени — единый источник истины для визуального стиля
- **GestureConfig**: пользовательские настройки жестов (вкл/выкл, чувствительность, тип haptic)
- **UserPreferences**: тема, размер текста, качество воспроизведения, настройки уведомлений
- **PerformanceBudget**: лимиты бандла, TTI, FPS — автоматически проверяемые в CI

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: Время загрузки первого экрана (TTI) ≤2 секунды на устройствах среднего класса
- **SC-002**: Плавность скролла ≥55 FPS в библиотеке с 200+ треками
- **SC-003**: Размер бандла снижен с 918КБ до ≤880КБ
- **SC-004**: Переходы между экранами <300мс (p95)
- **SC-005**: 4 из 5 новых пользователей определяют главное действие экрана за 10 секунд
- **SC-006**: Время создания нового экрана разработчиком ≤30 минут с использованием шаблонов
- **SC-007**: 0 компонентов >500 строк (текущее: 33 файла)
- **SC-008**: Lighthouse Performance score ≥95 на мобильных (текущее: 92)
- **SC-009**: Все настройки пользователя сохраняются и восстанавливаются между сессиями
- **SC-010**: 80% пользователей используют хотя бы 1 жест (свайп, долгое нажатие, двойной тап) в первую неделю

## Assumptions

- Целевые устройства: бюджетные Android (Pixel 5 / аналоги) и iPhone 12+
- Основной контекст использования: Telegram Mini App на мобильном
- Существующая дизайн-система (shadcn/ui + Tailwind) сохраняется и расширяется, не заменяется
- Текущая архитектура (React 19 + Zustand + TanStack Query) не меняется
- Оптимизация бандла достигается за счёт устранения дубликатов (6 пар), выбора одной DnD-библиотеки (-50КБ), и tree-shaking
- Haptic feedback доступен через Telegram Web App SDK
- Storybook уже настроен в проекте
