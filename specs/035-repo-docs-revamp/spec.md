# Спецификация: Редизайн документации репозитория

**Feature Branch**: `035-repo-docs-revamp`
**Created**: 2026-06-29
**Status**: Draft
**Input**: Обновление документации репозитория: навигация, README с прогрессом, оформление для клиентов и инвесторов

## User Scenarios & Testing

### User Story 1 — Инвестор оценивает проект (Priority: P1)

Инвестор открывает GitHub-репозиторий и за 3 минуты понимает: что делает проект, на какой стадии находится, кто команда, какой прогресс, какие метрики. Вся ключевая информация доступна из главного README без необходимости переходить по ссылкам.

**Why this priority**: Инвесторы — ключевая аудитория для привлечения финансирования. Если README не отвечает на их вопросы за 3 минуты — они уходят.

**Independent Test**: Открыть README.md в GitHub, засечь 3 минуты. Проверить: видна ли миссия проекта, текущий статус, метрики роста, roadmap, команда, контакты — без перехода по внешним ссылкам.

**Acceptance Scenarios**:

1. **Given** инвестор открывает README, **When** он скроллит первые 2 экрана, **Then** он видит: название, слоган, статус-шилдсы (build, coverage, bundle), 3 ключевых метрики, скриншот интерфейса
2. **Given** инвестор хочет понять прогресс, **When** он ищет раздел прогресса, **Then** он видит визуальную дорожную карту с выполненными, текущими и запланированными задачами с процентами выполнения
3. **Given** инвестор хочет увидеть продукт, **When** он смотрит на README, **Then** он видит скриншоты ключевых экранов приложения (главная, плеер, студия)

---

### User Story 2 — Разработчик быстро находит нужную документацию (Priority: P1)

Новый разработчик клонирует репозиторий и через DOCUMENTATION_INDEX.md находит всё необходимое для старта работы: архитектуру, конвенции кода, структуру проекта, руководство по настройке окружения — за 5 минут.

**Why this priority**: Быстрый онбординг разработчиков критичен для скорости разработки и снижения нагрузки на тимлидов.

**Independent Test**: Дать новому разработчику ссылку на репозиторий. Через 5 минут спросить где найти: структуру компонентов, конвенции коммитов, архитектуру аудио, расположение API-слоя. Все ответы должны быть найдены без подсказок.

**Acceptance Scenarios**:

1. **Given** разработчик открывает репозиторий, **When** он переходит в DOCUMENTATION_INDEX.md, **Then** он видит ролевую навигацию: «Я фронтендер», «Я бэкендер», «Я дизайнер», «Я PM» — каждый путь ведёт к релевантным документам
2. **Given** разработчик ищет архитектурную документацию, **When** он открывает ARCHITECTURE_HUB.md, **Then** он видит актуальные Mermaid-диаграммы и ссылки на 12 ADR с датами и статусами
3. **Given** разработчик хочет понять конвенции кода, **When** он читает CLAUDE.md, **Then** он видит все критические правила, нарушение которых сломает билд

---

### User Story 3 — Клиент/пользователь изучает возможности (Priority: P2)

Потенциальный пользователь (музыкант, AI-энтузиаст) заходит в репозиторий и понимает: что это за продукт, как его попробовать, какие функции есть, как выглядит интерфейс.

**Why this priority**: Репозиторий — часть воронки привлечения пользователей. Понятная презентация увеличивает конверсию в установку.

**Independent Test**: Показать README человеку, не знакомому с проектом. Спросить: «Что делает этот проект?», «Как его запустить?», «Какие функции есть?». Все три вопроса должны получить ответ без дополнительных пояснений.

**Acceptance Scenarios**:

1. **Given** пользователь открывает README, **When** он доходит до раздела «Что такое MusicVerse AI», **Then** он видит краткое описание на русском языке с ключевыми цифрами (количество функций, пользователей, треков)
2. **Given** пользователь хочет увидеть интерфейс, **When** он скроллит README, **Then** он видит галерею скриншотов с подписями
3. **Given** пользователь хочет попробовать, **When** он ищет ссылку на запуск, **Then** он находит Telegram-ссылку на бота и QR-код

---

### User Story 4 — Контрибьютор понимает процесс (Priority: P2)

Open-source контрибьютор хочет внести вклад и ищет: какие задачи доступны, как настроить окружение, какой процесс ревью, какие стандарты кода.

**Why this priority**: Open-source вклад ускоряет разработку и повышает качество кода. Чем проще контрибьюторам — тем больше PR.

**Independent Test**: Симулировать путь контрибьютора: найти CONTRIBUTING.md → найти good first issues → понять процесс PR → настроить окружение. Все шаги должны быть выполнимы без дополнительных вопросов.

**Acceptance Scenarios**:

1. **Given** контрибьютор открывает CONTRIBUTING.md, **When** он читает документ, **Then** он видит: визуальную схему процесса (fork→implement→lint→commit→PR→CI→review→merge), требования к коду, соглашение о коммитах
2. **Given** контрибьютор ищет задачи, **When** он переходит по ссылке на issues, **Then** он видит issues с меткой «good first issue» и понятным описанием

---

### User Story 5 — Документация поддерживается в актуальном состоянии (Priority: P3)

Любой участник команды может быстро обновить документацию после изменений в проекте, следуя чек-листу в MAINTENANCE.md. Документация не устаревает более чем на 2 недели.

**Why this priority**: Устаревшая документация хуже её отсутствия — она вводит в заблуждение. Но это сервисная задача, не блокирующая основную разработку.

**Independent Test**: Проверить MAINTENANCE.md — актуален ли он. Проверить все основные .md файлы — даты последнего обновления не старше 2 недель. Проверить перекрёстные ссылки — все ведут на существующие файлы.

**Acceptance Scenarios**:

1. **Given** разработчик завершил спринт, **When** он следует чек-листу в MAINTENANCE.md, **Then** он обновляет: PROJECT_STATUS.md, CHANGELOG.md, ROADMAP.md — все ссылки остаются рабочими
2. **Given** в проект добавляется новый компонент, **When** документатор проверяет чек-лист, **Then** он добавляет запись в REPOSITORY_STRUCTURE.md и обновляет CLAUDE.md
3. **Given** любой участник проверяет документацию, **When** он открывает MAINTENANCE.md, **Then** он видит актуальные инструкции, ссылающиеся на существующие файлы

---

### Edge Cases

- Что происходит, когда документация на русском, а контрибьютор — англоговорящий? → Ключевые governance-файлы (CONTRIBUTING, SECURITY, CODE_OF_CONDUCT) остаются на английском
- Как обрабатывать мёртвые ссылки в документации? → Ежемесячная проверка через CI-скрипт `check-md-links`
- Как быть с огромным KNOWLEDGE_BASE.md (733 строки)? → Разделить на тематические документы в docs/
- Что если скриншоты устаревают после редизайна? → Автоматическая генерация скриншотов через Playwright (уже есть screenshots/command)

## Requirements

### Functional Requirements

- **FR-001**: Главный README.md ДОЛЖЕН содержать: название проекта, слоган, статус-шилдсы (build, coverage, bundle, health), 3 ключевых метрики, скриншот интерфейса, краткое описание, навигационные ссылки на основные разделы
- **FR-002**: README.md ДОЛЖЕН содержать раздел «Прогресс проекта» с визуальной дорожной картой (Mermaid Gantt или таблица) — выполненные, текущие и запланированные задачи с процентами
- **FR-003**: README.md ДОЛЖЕН содержать раздел «Быстрый старт» с 5 командами для запуска проекта локально
- **FR-004**: README.md ДОЛЖЕН содержать блок «Скриншоты» с 4-6 изображениями ключевых экранов приложения
- **FR-005**: DOCUMENTATION_INDEX.md ДОЛЖЕН содержать ролевую навигацию: пути для фронтендера, бэкендера, дизайнера, PM, инвестора — каждый путь с 3-5 ссылками на релевантные документы
- **FR-006**: Все .md файлы в корне репозитория ДОЛЖНЫ иметь единый стиль: футер с навигационными ссылками (предыдущий/следующий раздел + на DOCUMENTATION_INDEX) и дату последнего обновления
- **FR-007**: PROJECT_STATUS.md ДОЛЖЕН быть обновлён до актуального состояния: отражать завершение 033-mobile-ui-improvements (114/114) и текущий спринт 035
- **FR-008**: MAINTENANCE.md ДОЛЖЕН быть актуализирован: удалены ссылки на несуществующие файлы, обновлены процедуры, дата актуализации — не старше 1 недели
- **FR-009**: KNOWLEDGE_BASE.md ДОЛЖЕН быть разделён на тематические документы в docs/ или удалён с переносом актуальной информации в соответствующие файлы (CLAUDE.md, ARCHITECTURE_HUB.md, PROJECT_STATUS.md)
- **FR-010**: Все ключевые .md файлы ДОЛЖНЫ иметь дату последнего обновления в формате «Обновлено: ДД.ММ.ГГГГ»
- **FR-011**: README.md ДОЛЖЕН содержать блок «Для инвесторов» с ключевыми метриками: количество пользователей, темп роста, ARPU (если применимо), стадия проекта
- **FR-012**: README.md ДОЛЖЕН содержать блок «Контакты и ссылки»: Telegram-бот, сайт, email, сообщество
- **FR-013**: Все документы для внешней аудитории (README, ROADMAP, CHANGELOG) ДОЛЖНЫ быть на русском языке
- **FR-014**: Технические governance-файлы (CONTRIBUTING, SECURITY, CODE_OF_CONDUCT) ДОЛЖНЫ оставаться на английском для международного open-source сообщества
- **FR-015**: Визуальное оформление ДОЛЖНО активно использовать: шилдсы (shields.io), иконки, Mermaid-диаграммы, таблицы, цитаты (blockquotes), разделители

### Key Entities

- **Document**: Файл .md в репозитории. Атрибуты: путь, язык (RU/EN), целевая аудитория (инвестор/разработчик/клиент), дата обновления, статус актуальности
- **Documentation Link**: Перекрёстная ссылка между документами. Атрибуты: исходный документ, целевой документ, текст ссылки, статус (рабочая/битая)
- **Screenshot**: Изображение интерфейса в документации. Атрибуты: путь к файлу, экран приложения, дата создания, alt-текст

## Success Criteria

### Measurable Outcomes

- **SC-001**: Инвестор находит ответы на 5 ключевых вопросов (что, зачем, стадия, метрики, команда) в README.md за 3 минуты
- **SC-002**: Новый разработчик находит необходимую документацию для старта работы за 5 минут через DOCUMENTATION_INDEX.md
- **SC-003**: 100% перекрёстных ссылок в документации ведут на существующие файлы (0 битых ссылок)
- **SC-004**: Все governance-файлы (CONTRIBUTING, SECURITY, CODE_OF_CONDUCT, AGENTS, CLAUDE) имеют дату обновления не старше 2 недель
- **SC-005**: README.md содержит не менее 4 скриншотов интерфейса приложения
- **SC-006**: KNOWLEDGE_BASE.md сокращён с 733 строк до 0 строк (полностью разделён по целевым документам)
- **SC-007**: MAINTENANCE.md не содержит ссылок на несуществующие файлы (0 broken references)
- **SC-008**: 90% корневых .md файлов имеют единый стиль футера с навигацией и датой обновления

## Assumptions

- Скриншоты интерфейса будут созданы через Playwright (уже настроен в проекте) или сделаны вручную
- Telegram-бот уже развёрнут и доступен по ссылке — указываем актуальную
- Метрики для инвесторов (количество пользователей, ARPU) будут предоставлены продуктовой командой или заменены на публично доступные данные
- Разделение KNOWLEDGE_BASE.md не требует удаления ценной информации — только перенос в правильные документы
- Русский язык для внешней документации является требованием продукта — английские версии при необходимости создаются отдельно
- Все изменения в документации проходят через стандартный PR-процесс с ревью
