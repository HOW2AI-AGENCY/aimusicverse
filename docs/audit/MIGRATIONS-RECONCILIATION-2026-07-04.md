# Сверка миграций (Sprint 050-A3) — 2026-07-04

**Метод:** реальная накатка на локальный PostgreSQL 16 (initdb-кластер), каждая миграция в отдельной транзакции — ровно как их применяет стандартный supabase-раннер. Минимальный срез схемы: `profiles`, `tracks`, `track_versions`, `track_likes` (оригинальная форма до Sprint 049) + стаб `auth.uid()`/roles для RLS-миграций. Прод недоступен из этой среды (Supabase MCP видит только чужой INACTIVE-проект), поэтому вердикт по проду — по косвенным свидетельствам (коммиты Lovable).

## Вопрос A3: конфликтуют ли пересекающиеся likes-миграции?

**Нет.** `20260704014859` (Lovable) — почти дословная копия `20260703120000` (Sprint 049); повторная накатка поверх первой прошла чисто (все шаги идемпотентны: `IF NOT EXISTS`, backfill по `WHERE ... IS NULL`, DO-блок пересоздаёт constraint). Функциональный тест после полной цепочки — все сценарии зелёные:

| Сценарий                                                | Результат |
| ------------------------------------------------------- | --------- |
| Legacy-лайк без версии backfill'ится на активную версию | ✅        |
| Лайк трека без версий удаляется (не блокирует NOT NULL) | ✅        |
| INSERT без версии → триггер резолвит активную           | ✅        |
| INSERT с версией → `track_id` выводится из версии       | ✅        |
| Дубль (user, version) → unique violation                | ✅        |
| Счётчики tracks/track_versions inc/dec                  | ✅        |

## Найденные проблемы и фиксы (все — в этой ветке)

### 1. 🔴 `20260703130000_homepage_genre_index.sql` ломал накатку с нуля

`CREATE INDEX CONCURRENTLY` не может выполняться внутри транзакции — воспроизведено: `ERROR: CREATE INDEX CONCURRENTLY cannot run inside a transaction block`. Именно поэтому Lovable продублировал индекс non-concurrently внутри `014859`. **Фикс:** заменён на обычный `CREATE INDEX IF NOT EXISTS` (индекс мал на текущем объёме; для сред, где `014859` уже прошёл — no-op).

### 2. 🔴 Дубль версии миграции `20260708000000_*` (Sprint 053/054)

`20260708000000_midi_source.sql` и `20260708000000_sound_effects.sql` имели одинаковый 14-значный префикс версии — supabase-раннер использует его как первичный ключ `schema_migrations`, вторая миграция упала бы с duplicate key. **Фикс:** `sound_effects` переименована в `20260708000001_sound_effects.sql`.

### 3. 🔴 Опечатка `timestamstz` в `sound_effects`

`updated_at timestamstz` → `ERROR: type "timestamstz" does not exist` — миграция Sprint 053 упала бы и на проде. **Фикс:** `timestamptz`. Накатка после фикса — OK.

### 4. 🟠 Регрессия: `profiles.stats_likes_received` перестал обновляться

Хотфикс `20260704015457` (Lovable, «убрал несуществующую колонку») убрал из `update_track_likes_count()` обновление `profiles.stats_likes_received`. Колонка существует в схеме репозитория (`20251212200000_extend_profiles_social.sql`) — на проде она, судя по хотфиксу, отсутствовала (дрейф). Подтверждено на срезе: владелец с 2 живыми лайками имеет `stats_likes_received = 0`. **Фикс:** новая миграция `20260709000000_restore_profile_like_stats.sql` — `ADD COLUMN IF NOT EXISTS` (закрывает дрейф) + backfill из живых лайков + восстановленный триггер. Проверена на срезе, включая сценарий дрейфа (колонка предварительно удалена): backfill корректен, inc/dec работают.

## Что осталось (вне досягаемости этой среды)

- Применить `20260709000000` на прод (через supabase db push / Lovable) и убедиться, что `schema_migrations` на проде согласована с директорией `supabase/migrations/` (какие из `20260703120000`/`130000` там числятся применёнными).
- 053 добавляет новые миграции — правило из плана закрытия действует: новые миграции только после этой сверки (выполнено).
